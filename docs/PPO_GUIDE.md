# 추가 실험: PPO로 배치 정책 미세 조정

> 대상: `src/ppo_train.py`
> 출발점: 최종 Agent v6의 GA 가중치
> 확인한 것: 그래디언트 계산이 수치 미분과 일치(오차 1e-9 수준), 학습 루프가 끝까지 돌아감, 결과 `model.json`이 제출 검증을 통과함
> 확인하지 않은 것: **성능이 오르는지.** 반드시 v6와 맞대결로 판단한다.

---

## 0. 한 줄 요약

> v6의 점수 공식을 **확률적인 정책**으로 바꾼 뒤(점수가 높을수록 자주 고름), 경기 결과를 보고 **"좋은 결과로 이어진 배치는 더 자주, 나쁜 결과로 이어진 배치는 덜 고르도록"** 가중치를 직접 고친다. 이것이 PPO(정책 기반 RL)다.

---

## 1. 기초 용어

| 용어 | 뜻 | 이 프로젝트에서 |
|---|---|---|
| 정책 기반 RL (policy gradient) | 가치를 거치지 않고 정책 π(a\|s) 자체를 직접 고치는 방법 | 가중치 w를 직접 업데이트 |
| 확률적 정책 | 행동을 확률로 고르는 정책 | 후보 배치마다 softmax 확률 |
| softmax 온도 T | 확률을 얼마나 고르게 퍼뜨릴지 | T가 작으면 1등만, 크면 골고루 (탐험) |
| Actor | 행동을 고르는 쪽 (정책) | logit = w · 특징 / T |
| Critic | 상태의 가치를 추정하는 쪽 | V(s) = c + u · (정책이 고를 배치들의 평균 특징) |
| Advantage A | "이 행동이 평소보다 얼마나 좋았나" | 실제 결과 − critic의 예상 |
| GAE(λ) | advantage를 노이즈와 편향 사이에서 균형 있게 계산하는 방법 | λ = 0.95 |
| on-policy | 현재 정책으로 모은 데이터로만 학습 | 반복마다 새로 경기 |
| 비율 r | 새 정책 확률 ÷ 예전 정책 확률 | 같은 데이터로 여러 번 업데이트할 때 필요 |
| 클리핑 (clip) | r이 1 ± 0.2를 넘으면 더 밀지 않음 | 한 번에 정책이 너무 바뀌는 걸 막음 = PPO의 핵심 |
| KL | 정책이 얼마나 바뀌었는지 | 0.02를 넘으면 그 반복의 업데이트를 멈춤 |
| 엔트로피 | 정책이 얼마나 골고루 고르는지 | 너무 빨리 한 수만 고르게 되는 걸 약간 막음 |

## 2. 구조

### 정책 (Actor)

v6가 하던 일을 거의 그대로 쓴다. 차이는 **"1등만 고르기" 대신 "점수에 비례한 확률로 고르기"**라는 점이다.

```text
후보 배치 약 60~68개 (현재 조각 + hold 조각)
  ↓ 각 후보의 특징 16개 φ
logit = (w · φ) / T
  ↓ softmax
확률 π(a|s) → 그 확률로 하나를 뽑아서 실행 (학습 중)
            → 가장 높은 것을 실행 (평가·실전)
```

w는 **v6의 GA 가중치로 시작**한다. 그래서 처음부터 v6와 비슷한 수준에서 출발하고, PPO는 미세 조정만 한다. 무작위에서 시작하면 학습이 매우 오래 걸린다.

**온도 T = 1**로 잡은 근거: v6 가중치로 실제 경기 274번의 결정을 측정해 보니, 1등과 2등 후보의 점수 차이 중앙값이 약 0.5였다. T = 2에서는 1등 확률이 평균 0.59, T = 5에서는 0.39였다. 앞의 RL 실험에서 무작위 배치 5%만으로도 크게 약해졌기 때문에, 탐험이 너무 많지 않도록 T = 1에서 시작한다.

### 가치 (Critic)

```text
V(s) = c + u · E_π[φ]
```

"지금 정책이 고를 배치들의 평균 특징"으로 상태를 요약하고, 그걸로 앞으로의 리턴을 예측하는 선형 함수다. 반복마다 몬테카를로 리턴에 ridge 회귀로 맞춘다.

### 보상

Step 6 RL과 같다. 공격 1줄당 +0.05, 경기 끝에 승리 +1 / 패배 −1, γ = 0.98.

### Step 6 RL과의 차이

| | Step 6 (가치 기반) | PPO (정책 기반) |
|---|---|---|
| 학습하는 것 | 보정값 V를 새로 학습해서 GA 점수에 더함 | **GA 가중치 w 자체**를 고침 |
| 행동 선택 | 점수 최고 (+ ε 확률로 무작위) | 점수에 비례한 확률 |
| 업데이트 | "이 보드 뒤의 리턴"을 회귀로 맞춤 | "평소보다 좋았던 행동의 확률을 올림" |
| 안전장치 | β를 작게 | 클리핑 + KL 조기 종료 |

## 3. 한 반복(iteration)에서 일어나는 일

```text
① 현재 정책(확률적)으로 40경기 → 결정마다 후보 특징, 고른 번호, 그 확률, 보상 기록
② critic: 평균 특징 → 리턴 G를 회귀로 맞춤
③ GAE(λ)로 결정마다 advantage A 계산 → 평균 0, 표준편차 1로 정규화
④ 같은 데이터로 최대 4번(epoch) 업데이트:
     목표 = mean( min( r·A, clip(r, 0.8, 1.2)·A ) ) + 0.001 · 엔트로피
     KL이 0.02를 넘으면 그 반복은 거기서 멈춤
⑤ 새 가중치로 iterXX_model.json 저장
```

계산은 모두 numpy로 직접 했다. 정책이 "특징의 선형 함수 + softmax"라서 그래디언트를 식으로 바로 쓸 수 있다.

```text
∇_w log π(a|s) = ( φ_a − Σ_b π_b φ_b ) / T
```

"고른 배치의 특징 − 정책이 평균적으로 고르는 특징" 방향으로 w를 민다는 뜻이다. advantage가 양수면 그 방향으로, 음수면 반대로 민다.

## 4. 실행

```bash
cd ~/projects/tetris-ai-agent
source .venv/bin/activate
nohup python src/ppo_train.py --init agents/my_agent/model.json \
  --vs agents/my_agent/model.json agents/v5_d2/model.json \
  --iters 30 --games 40 --workers 10 --out results/ppo > results/ppo.log 2>&1 &
tail -f results/ppo.log
```

- 상대: v6 자신과 v5 (학습 속도를 위해 상대는 1수 탐색으로 실행)
- 예상 시간: 반복당 30~60초, 30회면 **20~30분**

### 로그 읽기

```text
[iter 05] decisions=24000 train_win=0.48 entropy=0.60 kl=0.0150 clip=0.03 41s -> iter05_model.json
```

| 항목 | 뜻 | 좋은 범위 |
|---|---|---|
| `decisions` | 이번 반복의 배치 결정 수 | — |
| `train_win` | 학습 중(확률적 선택) 승률 | 0.4~0.6 근처에서 서서히 오르면 좋음 |
| `entropy` | 정책이 얼마나 골고루 고르나 | 갑자기 0 가까이 떨어지면 탐험이 사라진 것 |
| `kl` | 이번 반복에서 정책이 바뀐 정도 | 0.005~0.03 |
| `clip` | 클리핑에 걸린 비율 | 0.0~0.2 |

**문제 신호**
- `kl`이 계속 0.03을 넘음 → `--lr`을 0.005로 낮춘다
- `train_win`이 계속 떨어짐 → 학습이 망가지는 중. 멈추고 `--lr`을 낮추거나 `--temp`를 0.5로 낮춘다
- `entropy`가 0.1 아래로 떨어짐 → 정책이 굳었다. `--ent`를 0.005로 올린다

| 옵션 | 기본값 | 뜻 |
|---|---:|---|
| `--temp` | 1.0 | softmax 온도 |
| `--lr` | 0.01 | 학습률 (Adam) |
| `--clip` | 0.2 | 클리핑 범위 |
| `--epochs` | 4 | 같은 데이터로 업데이트하는 횟수 |
| `--target-kl` | 0.02 | 정책 변화 상한 |
| `--ent` | 0.001 | 엔트로피 보너스 |
| `--iters`, `--games` | 30, 40 | 반복 수, 반복당 경기 수 |

## 5. 평가

저장된 `model.json`에는 v6의 2수 앞보기 설정은 들어가고, Step 6의 V는 **들어가지 않는다**(PPO 정책은 V 없이 학습했기 때문). 평가는 지금까지와 같이 **v6와 맞대결**로 한다.

### 1차: 반복 3개를 40경기씩

```bash
cat > eval_ppo.sh <<'EOF'
for it in 09 19 29; do
  rm -rf agents/cand_ppo$it
  cp -r agents/my_agent agents/cand_ppo$it
  cp results/ppo/iter${it}_model.json agents/cand_ppo$it/model.json
  sed -i "s/\"id\": \"[^\"]*\"/\"id\": \"myteam_ppo_$it\"/; s/\"name\": \"[^\"]*\"/\"name\": \"PPO iter $it\"/" agents/cand_ppo$it/manifest.json
  echo "iter $it: $(python kits/tetris_competition_kit_v2/tools/evaluate.py agents/cand_ppo$it agents/my_agent --games 40 --seed 10000000 | tail -1)"
done
EOF
nohup bash eval_ppo.sh > results/eval_ppo.log 2>&1 &
```

30~40분 뒤 `cat results/eval_ppo.log`로 확인한다.

### 2차: 가장 좋았던 반복만 100경기

```bash
python kits/tetris_competition_kit_v2/tools/evaluate.py agents/cand_ppo29 agents/my_agent --games 100 --seed 10100000 | tail -1
```

(가장 좋았던 반복 번호로 바꾼다.) 1차에서 셋 중 1등을 골랐으므로 선택 편향이 있다. 그래서 2차 결과만으로 판단한다. **60승 이상이면 PPO가 v6를 넘은 것이다.**

## 6. 예상 결과와 한계

- **v6가 이미 강해서 개선 폭은 작을 수 있다.** GA로 찾은 가중치가 이미 좋은 지점이라, PPO는 그 근처를 다듬는 정도다.
- **노이즈가 크다.** 승패 보상은 경기 끝에 한 번이고 조각 운이 크다. 반복당 40경기는 PPO 기준으로 적은 편이다. `--games 80`으로 늘리면 안정되지만 시간이 두 배다.
- **학습은 1수, 평가는 2수다.** 학습 중에는 빠르게 1수 탐색으로 고르고, 평가 때는 v6처럼 2수 앞보기를 켠다. 1수 기준으로 좋아진 가중치가 2수에서도 좋다는 보장은 없다.
- **선형 정책이다.** 특징 16개의 선형 함수라 표현력은 GA와 같다. 차이는 "찾는 방법"뿐이다. 그래서 이 실험은 **"같은 정책 공간에서 GA와 PPO 중 어느 쪽이 더 잘 찾나"**를 비교하는 실험이기도 하다.

어떤 결과가 나와도 README의 "추가 실험"으로 기록할 가치가 있다. 세미나에서 다룬 PPO를 실제 대전 환경에 적용하고, GA와 직접 비교한 결과가 되기 때문이다.
